# A Go service

What enola measures in a Go codebase, and the laws worth writing where
the compiler already forbids an import cycle. The worked example is
[`examples/go-service`](../examples/go-service): a chi service in four
packages that breaks two laws on purpose, snapshotted by CI on every
change to this repository.

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/enola-labs/enola/main/install.sh | sh
enola --version
```

enola is written in Go, and a source build is `go install ./cmd/enola`
from a clone of [enola-labs/enola](https://github.com/enola-labs/enola),
with Go 1.26 or newer and a C compiler for the tree-sitter bindings. The
prebuilt binary needs neither. Then the loop from
[start here](01-start-here.md).

## What enola measures

- **Packages are modules**, imports are `imports` edges between them, and
  calls are `calls` edges from the function that makes them, including a
  function used as a value (a dispatch-table entry, a callback).
- **Routes** from `net/http`, gin, chi and the other routers, with prefixes
  composed across function boundaries; outbound HTTP calls as client
  routes; gRPC and Kafka on both sides.
- **Loops**: a call made inside a loop over input is recorded on the
  caller, which is what `query-loops` reads for N+1 candidates.
- **Multi-module repositories**: imports resolve through every `go.mod`
  in the repository, so a monorepo with one module per service, or a
  module nested in another, gets internal edges between them rather than
  external, unresolved ones.

## The laws

Go's compiler refuses an import cycle between packages, so gating on
`cycles` enforces what the toolchain enforces first. The laws a Go team
needs are the ones no compiler states: which package may reach which.

```yaml
use_recipe:
  - recipe: layered
    as: shop
    mode: ratchet
    bind:
      presentation: { match: ["internal/web/**"] }
      application: { match: ["internal/checkout/**"] }
      domain: { match: ["internal/order/**"] }
      infrastructure: { match: ["internal/store/**"] }
```

```text
Constraint shop/presentation-reaches-application-only violated: internal/web.listRecent -> internal/store.RecentOrders via calls
```

**The recipe's two domain rules read `depends_on`, and Go's extractor
writes `imports`,** so they are silent on a Go tree. State the domain's
law over imports:

```yaml
components:
  - name: domain
    match: ["internal/order/**"]
  - name: storage
    match: ["internal/store/**"]
rules:
  - id: the-domain-imports-no-storage
    forbid: domain
    to: storage
    via: imports
    mode: ratchet
    because: "The domain is the part that outlives the database; a domain package that imports the store cannot be tested or reasoned about without it."
```

```text
Constraint the-domain-imports-no-storage violated: internal/order -> example.com/shop/internal/store -> internal/store via imports
```

Go's own `internal/` rule stops another module importing your internals;
a `forbid` between two of your own `internal/` packages is the rule it
leaves to you.

## Dependencies

A `require` in `go.mod` names an exact version, so every direct
dependency is pinned and `supply-chain` holds; the example binds it and
it reports that its part matches nothing. `// indirect` lines are the
closure and are not read.
